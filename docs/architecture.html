01 — What Changed

Before vs After

From a tightly-coupled monolith to a loosely-coupled platform with runtime plugin discovery

BEFORE Tight Coupling

  • ✗ Every service hardcoded via @register_service decorator in PyWorkspace code
  • ✗ Agent tools compiled into agent/tools/ directory — requires code merge
  • ✗ No event system — components can't react to workspace lifecycle
  • ✗ Adding PySandbox = modify 5+ files in PyWorkspace repo
  • ✗ All teams must commit to the same repo and release cycle
  • ✗ A bug in one team's code can break the whole platform
➔

AFTER Loose Coupling

  • ✓ Services discovered at runtime via YAML manifest or HTTP endpoint
  • ✓ Agent tools invoked via HTTP — RemoteTool calls plugin API
  • ✓ Event bus with webhook delivery — plugins react to lifecycle events
  • ✓ Adding PySandbox = drop a YAML manifest or POST to /v1/plugins/register
  • ✓ Each team owns their repo, CI/CD, and deployment independently
  • ✓ Plugin failures are isolated — logged, not propagated

03 — Plugin System

How the Plugin System Works

The core innovation: components describe themselves via manifests, PyWorkspace discovers them at runtime

✎ Manifest

Each component publishes a PluginManifest — a Pydantic schema describing its name, API URL, tools, service spec, and event subscriptions. This is the contract.

YAML JSON HTTP

⚙ Registry

The PluginRegistry holds all discovered manifests in memory. It indexes tools for fast lookup and tracks which plugins subscribe to which events.

Singleton Thread-safe reads

↹ Loader

The PluginLoader discovers manifests from three sources: local files (ConfigMap), HTTP endpoints (self-describing services), and API calls (POST to /v1/plugins/register).

File HTTP API

Plugin Manifest Schema

Every external component defines this contract. PyWorkspace consumes it — no code import needed.

# pysandbox.yaml — owned by Sandbox Team, in their own repo kind: PyWorkspacePlugin name: pysandbox version: "1.0.0" display_name: PySandbox description: Isolated code execution with gVisor/Firecracker team: sandbox-team categories: [runtime, security] # How to reach this plugin base_url: http://pysandbox.internal:8080 auth_type: api_key # Optional: run as a workspace sidecar pod service: image: yourorg/pysandbox:1.0.0 port: 8080 health_check: { endpoint: /healthz } resources: { cpu: "1.0", memory: "2Gi" } # Tools the PyOz agent can call (via HTTP, not code import) tools: - name: sandbox_execute endpoint: /v1/sandbox/execute method: POST input_schema: { ... } # Event integration (decoupled communication) events: publishes: [sandbox.completed, sandbox.failed] subscribes: [workspace.created, workspace.destroyed] callback_url: http://pysandbox.internal:8080/webhooks/events

Three Ways to Register a Plugin

METHOD 1

File-Based (Dev/K8s)

Drop YAML files into /etc/pyworkspace/plugins/. Loaded on startup. In K8s, mount as a ConfigMap.

# settings PLUGIN_MANIFEST_DIR=/etc/pyworkspace/plugins # On startup, main.py calls: loader.load_from_directory(manifest_dir)

METHOD 2

HTTP Discovery

PyWorkspace fetches manifests from plugin endpoints: GET {base_url}/plugin/manifest

# settings PLUGIN_DISCOVERY_URLS=http://pysandbox:8080,http://pygate:8443 # On startup: loader.discover_plugins(urls)

METHOD 3

API Registration

Plugin POSTs its manifest to PyWorkspace on startup. Fully dynamic.

# Plugin's startup code: POST /v1/plugins/register { "name": "pysandbox", "base_url": "http://...", "tools": [...] }

How Agent Tools Work: Built-in vs Plugin

Built-in Tool (ConfiguredTool)

In-process execution. Tool code lives in agent/tools/.

@register_tool("sql_query") async def sql_query(host, port, credentials, **kwargs): # Direct database connection conn = await asyncpg.connect(host=host, ...) return await conn.fetch(kwargs["query"])
Execution: Agent calls Python function directly in same process

Plugin Tool (RemoteTool) NEW

HTTP execution. Tool code lives in the plugin's own service.

# No code in PyWorkspace! Manifest defines it: tools: - name: sandbox_execute endpoint: /v1/sandbox/execute method: POST # RemoteTool.execute() does: POST http://pysandbox:8080/v1/sandbox/execute { "code": "print('hello')", ... }
Execution: Agent sends HTTP POST to plugin endpoint. Zero code coupling.
The agent doesn't know the difference. Both implement async execute(**kwargs). build_tool_registry() seamlessly combines both types.

PluginServiceAdapter: The Bridge

The existing provisioner expects ServiceDefinition objects. The PluginServiceAdapter wraps a PluginManifest into that interface — so the provisioner works with plugin services without any changes.

04 — Event Bus

Decoupled Communication

Components publish events, other components react — without knowing about each other

⚡ In-Process Handlers

PyWorkspace's own modules subscribe with async functions. Used for internal reactions (audit logging, TTL tracking, etc.).

async def on_workspace_created(event: Event): await audit_log.record(event) event_bus.subscribe("workspace.created", on_workspace_created)

🌐 Webhook Delivery

External plugins receive events via HTTP POST to their callback_url. Fire-and-forget with error logging.

# PySandbox manifest declares: events: subscribes: [workspace.created] callback_url: http://pysandbox:8080/webhooks # PyWorkspace POSTs event JSON to that URL

Event Flow Example

1. Provisioner creates workspace

After creating the workspace record, the provisioner publishes a workspace.created event to the event bus.

2. Event bus fans out

The bus finds all in-process handlers and webhook URLs that subscribed to workspace.created. Runs them concurrently.

3. In-process: Audit log records event

Internal handler writes to workspace_audit_log table. Runs within PyWorkspace process.

4. Webhook: PySandbox pre-warms sandboxes

POST http://pysandbox:8080/webhooks/events — PySandbox receives the event and pre-creates sandbox environments for the new workspace. No PyWorkspace code change needed.

5. Webhook: PyReview sets up GitHub webhook

PyReview receives the same event and configures a GitHub webhook for the workspace repo. Also no PyWorkspace code change.

Standard Event Types

Event Type Source When Published Example Subscribers
workspace.created pyworkspace Workspace record created, before provisioning PySandbox (pre-warm), PyReview (setup webhooks)
workspace.provisioned pyworkspace All services healthy, workspace RUNNING PyTest-AI (start watching for code changes)
workspace.paused pyworkspace Workspace scaled to 0 Billing (stop metering), PyDebug (disconnect)
workspace.destroyed pyworkspace Namespace deleted, all resources cleaned PySandbox (cleanup), PyReview (remove webhooks)
service.healthy pyworkspace Service pod passes health check PyOz (add tool to available set)
plugin.registered pyworkspace New plugin manifest loaded Admin dashboard (update catalog UI)
sandbox.completed pysandbox Code execution finished in sandbox PyTest-AI (collect results), PyMigrate (validate)
llm.rate_limit.hit pygate LLM provider rate limited Monitoring (alert), PyOz (switch model)

06 — Integration Guide

How Teams Integrate

Step-by-step guide for any team building a new component

Step 1: Build your service in your own repo

Create github.com/yourorg/pysandbox with its own CI/CD pipeline. FastAPI/gRPC/whatever you prefer. No dependency on PyWorkspace code.

Step 2: Write your plugin manifest

Define a YAML/JSON file describing your API URL, tools (with input/output schemas), and event subscriptions. See examples/plugin-manifests/ for templates.

Step 3: Serve your manifest at GET /plugin/manifest

Add a single endpoint that returns your manifest as JSON. PyWorkspace can auto-discover you via HTTP. Alternatively, mount the YAML as a K8s ConfigMap.

Step 4: Register on startup

On your service startup, POST /v1/plugins/register to PyWorkspace with your manifest. Or rely on file/HTTP discovery (no code needed).

Step 5: Handle webhook events

If you subscribed to events (e.g., workspace.created), implement a webhook handler at your callback_url. You'll receive event JSON via POST.

Step 6: You're done. Deploy independently.

Your team deploys, scales, and updates your service on your own schedule. Zero PRs to PyWorkspace. Zero coordination with other teams. Update your manifest version when your API changes.
